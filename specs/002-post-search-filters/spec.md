# Feature Specification: Фильтры-уточнения (Post-Search Refinement Chips)

**Feature Branch**: `002-post-search-filters`
**Created**: 2026-02-08
**Status**: ✅ Implemented (2026-02-12)
**Commit**: caa254b | **PR**: #2 | **Merged to**: main
**Input**: User description: "Фильтры-уточнения (Post-Search Refinement Chips). После поиска авто пользователь видит динамические чипсы-фильтры, сгенерированные из реальных данных результатов поиска. Клик по чипсу фильтрует результаты на клиенте без нового запроса к LLM/бекенду. Группы фильтров: тип двигателя, КПП, привод, тип кузова, диапазон годов. Чипсы показываются только если есть что фильтровать (>1 уникального значения в группе). Множественный выбор внутри группы и между группами. Клик по активному чипсу снимает фильтр. Чисто фронтенд-фича, бекенд не трогаем."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Фильтрация результатов по одному параметру (Priority: P1)

Пользователь выполняет поиск автомобилей и получает результаты. Над списком карточек появляются чипсы-фильтры, сгенерированные из реальных данных найденных машин. Пользователь кликает на чипс (например, "дизель") и список мгновенно сужается до машин с этим параметром. Повторный клик по активному чипсу снимает фильтр и возвращает все результаты.

**Why this priority**: Основная ценность фичи — возможность быстро сузить результаты поиска без повторного обращения к LLM. Даже с одним фильтром пользователь получает ощутимую пользу.

**Independent Test**: Выполнить поиск "бумер x5 до 5 млн", убедиться что появляются чипсы по типу двигателя, кликнуть "дизель" — список сужается. Кликнуть ещё раз — фильтр снимается.

**Acceptance Scenarios**:

1. **Given** результаты поиска содержат авто с разными типами двигателя (дизель и бензин), **When** пользователь кликает чипс "дизель", **Then** отображаются только дизельные авто, чипс визуально выделен как активный
2. **Given** активный фильтр "дизель", **When** пользователь кликает по нему повторно, **Then** фильтр снимается, отображаются все результаты, чипс возвращается в неактивное состояние
3. **Given** результаты поиска содержат авто только с одним типом двигателя (все дизельные), **When** результаты отображаются, **Then** группа чипсов "тип двигателя" не показывается (нечего фильтровать)

---

### User Story 2 - Комбинирование нескольких фильтров (Priority: P1)

Пользователь применяет несколько фильтров одновременно — как внутри одной группы (например, "дизель" + "бензин"), так и между группами (например, "дизель" + "АКПП"). Фильтры внутри группы работают по логике ИЛИ (показать дизель или бензин), между группами — по логике И (дизель И полный привод).

**Why this priority**: Комбинирование фильтров — ключевой сценарий для пользователей с конкретными требованиями. Без этого фильтрация ограничена одним параметром.

**Independent Test**: Выполнить поиск с широкими результатами, выбрать "дизель" в типе двигателя и "АКПП" в КПП — убедиться что остаются только дизельные автоматы.

**Acceptance Scenarios**:

1. **Given** активный фильтр "дизель" в группе двигатель, **When** пользователь кликает "АКПП" в группе КПП, **Then** отображаются только дизельные авто с АКПП (логика И между группами)
2. **Given** активный фильтр "дизель" в группе двигатель, **When** пользователь кликает "бензин" в той же группе, **Then** отображаются авто с дизелем ИЛИ бензином (логика ИЛИ внутри группы)
3. **Given** комбинация фильтров даёт 0 результатов, **When** фильтры применены, **Then** пользователь видит сообщение "Нет авто по выбранным фильтрам" и все чипсы остаются доступными для изменения

---

### User Story 3 - Счётчик и сброс фильтров (Priority: P2)

Пользователь видит актуальное количество отфильтрованных результатов и может сбросить все фильтры одним действием. Это даёт ощущение контроля и прозрачности: пользователь всегда понимает сколько машин осталось после фильтрации.

**Why this priority**: Улучшает удобство, но не блокирует базовую функциональность фильтрации.

**Independent Test**: Применить 2-3 фильтра, убедиться что счётчик обновляется, нажать "Сбросить" — все фильтры снимаются.

**Acceptance Scenarios**:

1. **Given** результаты поиска без фильтров (15 авто), **When** пользователь применяет фильтр "дизель" (6 авто), **Then** счётчик обновляется: "Показано 6 из 15 машин"
2. **Given** активны несколько фильтров, **When** пользователь нажимает кнопку "Сбросить фильтры", **Then** все фильтры снимаются, отображаются все результаты, счётчик возвращается к исходному значению
3. **Given** нет активных фильтров, **When** пользователь смотрит на область фильтров, **Then** кнопка "Сбросить фильтры" скрыта или неактивна

---

### Edge Cases

- Что если результаты поиска содержат авто с пустыми значениями полей (нет данных о КПП/приводе)? — Авто с пустым значением поля исключаются из подсчёта чипсов этой группы и всегда проходят фильтр (не скрываются при любом выборе в группе)
- Что если после применения фильтров пользователь нажимает "Показать ещё" (подгрузка)? — Новые результаты также фильтруются по активным чипсам, чипсы обновляются с учётом новых данных
- Что если результат поиска — 1 авто? — Чипсы-фильтры не показываются (нечего фильтровать)
- Что если пользователь выполняет новый поиск? — Все активные фильтры сбрасываются, чипсы генерируются заново из новых результатов

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST генерировать чипсы-фильтры динамически из полей реальных результатов поиска
- **FR-002**: Система MUST поддерживать 5 групп фильтров: тип двигателя, КПП, привод, тип кузова, год выпуска
- **FR-003**: Система MUST скрывать группу фильтров, если все результаты имеют одинаковое значение в этой группе (нечего фильтровать)
- **FR-004**: Система MUST применять фильтры мгновенно на клиенте без обращения к серверу
- **FR-005**: Система MUST поддерживать множественный выбор: логика ИЛИ внутри группы, логика И между группами
- **FR-006**: Система MUST позволять снять фильтр повторным кликом по активному чипсу
- **FR-013**: Система MUST отображать на каждом чипсе количество совпадающих авто (например, "дизель (6)"), обновляемое при каждом изменении фильтров
- **FR-014**: Система MUST показывать чипсы с 0 совпадений в неактивном (disabled) состоянии с отображением "(0)" — чипс виден, но некликабелен, раскладка UI стабильна
- **FR-007**: Система MUST обновлять счётчик отображаемых результатов при каждом изменении фильтров
- **FR-008**: Система MUST предоставлять возможность сбросить все фильтры одним действием
- **FR-009**: Система MUST сбрасывать все фильтры при выполнении нового поиска
- **FR-010**: Система MUST показывать сообщение при пустом результате фильтрации (0 авто подходит)
- **FR-011**: Система MUST исключать авто с пустым значением поля из подсчёта чипсов этой группы и всегда показывать их в результатах (не скрывать при любом активном фильтре в группе)
- **FR-012**: Система MUST применять активные фильтры к вновь подгруженным результатам ("Показать ещё")

### Key Entities

- **Filter Group**: Категория фильтрации (двигатель, КПП, привод, кузов, год). Содержит название группы, ключ поля в данных авто и список доступных значений
- **Filter Chip**: Отдельное значение внутри группы (например, "дизель"). Имеет текстовую метку, состояние активности, количество совпадающих авто
- **Active Filters**: Набор текущих выбранных фильтров пользователя. Используется для клиентской фильтрации массива результатов

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Фильтрация результатов происходит мгновенно (пользователь не замечает задержки) при клике на чипс
- **SC-002**: Пользователь может сузить результаты поиска до нужных авто за 2-3 клика без повторного поиска
- **SC-003**: При любой комбинации фильтров система отображает корректное количество результатов или понятное сообщение об отсутствии совпадений
- **SC-004**: Новый поиск всегда начинается с чистого состояния фильтров — пользователь не запутывается в "застрявших" фильтрах от предыдущего запроса

## Assumptions

- Все данные для фильтрации уже присутствуют в объектах авто, полученных из результатов поиска (поля: engine_type, transmission, drive_type, body_type, year)
- Фильтрация происходит только на фронтенде — бекенд API не изменяется
- Группа "год" отображает конкретные года, присутствующие в результатах, а не произвольные диапазоны
- Порядок карточек авто после фильтрации сохраняется таким же, как в исходных результатах поиска

## Clarifications

### Session 2026-02-08

- Q: Как обрабатывать авто с пустыми значениями фильтруемых полей? → A: Исключать из группы — авто с пустым полем всегда проходят фильтр этой группы (не скрываются)
- Q: Показывать ли количество авто на чипсе? → A: Да, показывать счётчик на чипсе (например, "дизель (6)"), обновляемый динамически при изменении фильтров
- Q: Как показывать чипсы с 0 совпадений при активных фильтрах? → A: Показывать в disabled-состоянии с "(0)" — стабильная раскладка, пользователь видит что комбинация пуста

## Scope & Exclusions

**В скоупе**:
- 5 групп фильтров из полей каталога
- Клиентская фильтрация массива результатов
- Визуальные чипсы с состояниями (неактивный, активный)
- Счётчик и сброс фильтров

**Вне скоупа**:
- Фильтрация по цене (слайдер/range) — отдельная фича
- Сортировка результатов — отдельная фича
- Сохранение фильтров между сессиями
- Серверная фильтрация / изменение бекенд API
